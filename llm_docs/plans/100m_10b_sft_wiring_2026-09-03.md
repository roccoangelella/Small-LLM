# 100M/10B SFT wiring plan

## Goal

Make the completed 100M/10B endpoint a first-class SFT parent without selecting or accidentally inheriting a scientific SFT recipe.

Canonical parent:

```text
run:              100m-10b-deep-decay-from-step15500
checkpoint:       step-00076294
consumed targets: 10,000,007,168
transport:        verified Hugging Face Storage Bucket latest
```

## Completed in the first wiring slice

- Registered a dedicated `100M / 10B` SFT profile in `kaggle/sft_100m_10b.py`.
- Added `100M / 10B` profile discovery and dry-run visibility in `kaggle/sft_cli.py`.
- Made the profile explicitly fail-closed with `recipe_status=pending`, no target budget, and no LR selection.
- Added explicit `hf_storage_bucket` support to `post_training.sft.checkpoints.download_parent_checkpoint`, reusing the already verified bucket checkpoint downloader.
- Added regression coverage for exact parent identity, fail-closed launcher behavior, and bucket/latest parent resolution.
- Preserved all existing 100M/2B launcher semantics.

## Gate 1 — generalize the dual-T4 parent shim

`kaggle/dual_t4_sft.py` currently replaces `post_training.sft.train_cli.download_parent_checkpoint` with a helper that always calls `download_verified_model_artifact`. This was intentional for the completed 100M/2B parent but bypasses the new core transport selector.

Before 100M/10B can be enabled, the DDP shim must select parent transport explicitly and preserve both behaviors:

- 100M/2B: stable model artifact, existing behavior unchanged;
- 100M/10B: verified Storage Bucket `latest`, exact final endpoint.

The shim must never infer `best` and `latest` as interchangeable.

## Gate 2 — propagate transport through train and eval

The production SFT train/eval entrypoints and Kaggle runtime currently expose parent repo/run/pointer but not a first-class parent-transport argument. Add and bind an explicit transport selector through:

```text
kaggle/sft_cli.py
  -> kaggle/sft_scaled_runtime.py
  -> kaggle/dual_t4_sft.py / post_training.sft.train_cli
  -> post_training.sft.checkpoints.download_parent_checkpoint
```

and the equivalent parent path in `post_training.sft.eval_suite`.

Offline tests must assert that the 10B path resolves `step-00076294` semantics and that 2B still resolves its historical stable artifact path.

## Gate 3 — parent preflight

The current scaled-runtime preflight verifies only Git-backed stable model artifacts. Extend it to verify the configured bucket/latest parent when the profile requests Storage Bucket transport. The preflight must happen before W&B/GPU initialization and must fail on wrong run ID, missing pointer, wrong checkpoint ID, or consumed-token mismatch.

For 100M/10B specifically, the accepted identity check is:

```text
checkpoint_id == step-00076294
consumed_tokens == 10_000_007_168
```

Do not merely check that some `latest.json` exists.

## Gate 4 — recipe decision and immutable SFT dataset

Remain fail-closed until a separate ADR selects the 100M/10B SFT recipe. That later decision must pin at least:

- absolute/fractional SFT target horizon;
- source/replay allocation and held-out policy;
- LR schedule and numeric anchors;
- run ID / dataset ID;
- optimizer microbatch/cadence if they differ from qualified 100M/2B execution;
- qualification and promotion criteria.

ADR 0137's enlarged behavior evaluation remains a dependency for using new SFT experiments to choose among recipes.

## Verification policy

A wiring change is acceptable only when:

1. the launcher dry-run shows the exact parent transport/pointer/identity;
2. a real launch is impossible while `recipe_status=pending`;
3. bucket and stable-artifact parent-resolution tests pass;
4. existing 100M/2B SFT tests remain unchanged/passing;
5. no code path silently maps the 10B final endpoint to the separate strict-loss `best` artifact.
